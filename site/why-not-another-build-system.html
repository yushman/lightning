Every JVM build system is written in a JVM language. I wanted to know why.

July 2026 · on Gradle, Buck2, and the build system I decided not to write

Every mainstream build system for Java, Kotlin and Android runs on the JVM and is configured in a JVM language — Groovy or Kotlin. If you have spent an afternoon waiting on Gradle, the question writes itself: why not Go or Rust? Native startup, no daemon eating four gigabytes, declarative configuration like Cargo.toml instead of a Turing-complete script that can do literally anything.

I spent a while trying to answer that honestly, planning to build the thing. I didn't build it. Here is what changed my mind, because the reasoning turned out to be more interesting than the plan.

The premise is already falsified

The first surprise: it has been done. Buck2 is written in Rust, configured in Starlark, and builds Java, Kotlin and Android in production at Meta — millions of builds a day, including incremental Kotlin compilation through JetBrains' Build Tools API. Bazel keeps a Java core but moved configuration out of the JVM entirely, also to Starlark.

So the interesting question isn't "is it possible". It is: given that it's possible and demonstrably fast, why is everyone else still on the JVM?

Three structural reasons, none of them inertia

The compilers are JVM programs. javac, kotlinc, KSP, the Compose compiler — all of them run on the JVM. Whatever language your build system is written in, it ends up starting JVM processes. A non-JVM build system is not "a build system without the JVM"; it is an orchestrator around JVM compile workers. That is a smaller, more honest claim than the one I started with.

A warm compiler is the performance model. Incremental build speed comes from a long-lived JVM with a warmed-up JIT and populated caches. Gradle's memory-hungry daemon isn't an accident of implementation language you can optimize away — it is the mechanism. Replace the orchestrator with a native binary and you still need that warm JVM behind it; you have moved the memory, not removed it.

Plugins live inside the process. Build plugins call compiler APIs directly, run annotation processors, instrument bytecode. From a JVM language that is a method call. From Go or Rust it is an IPC protocol you now own, version, and debug — for every integration point in an ecosystem that has thousands.

The insight that actually mattered

Gradle is not slow because of Groovy. It is slow because of a model that cannot be cached.

Gradle's configuration phase executes arbitrary, Turing-complete code across every module of your project, and it can't be reliably cached precisely because that code can do anything — read the clock, hit the network, mutate another module's tasks. Buck2 is fast first and foremost because its configuration is declarative Starlark with no side effects, which makes the entire build graph hashable and cacheable.

Rust is a nice bonus there. Declarativeness is the foundation. If you took Buck2's model and implemented it on the JVM, you would still have most of the win; if you took Gradle's model and rewrote it in Rust, you would still have the problem. That single observation demolished the original plan, because the plan's whole premise was that the language was the lever.

Now the data point I keep coming back to. JetBrains set out to solve exactly the three pains I started from — speed, implicit magic, and imperative build scripts — and built their new tool in Kotlin again. People with a compiler team, an IDE team, and every incentive to escape the JVM looked at the same tradeoff and stayed. The structural reasons above outweigh a native core, and they know it better than I do.

The real moat is Android, not the JVM

Suppose you ignore all of that and write the orchestrator anyway. For plain Kotlin/JVM it's a real, finishable project — a few months of interesting work.

Then someone asks for Android, and the job changes shape. Now you must reproduce the surface of the Android Gradle Plugin: AAPT2, resource and manifest merging, R8 and D8, multidex, signing, baseline profiles, the Compose compiler plugin, KSP wiring, build variants and flavors — against a target that Google moves with every AGP release. This is why no "Gradle killer" exists for Android even though almost nobody enjoys Gradle. Meta can afford it because Meta has a build-infrastructure organization. A solo project cannot, and pretending otherwise is how side projects die at 80% done.

So I built the layer above instead

Here is where the reasoning led. The valuable, unoccupied position isn't replacing the build. It is everything around the build that nobody has open-sourced for Gradle: knowing which tests are flaky and since when, knowing why a build got slower, caching artifacts across machines, and deciding what a diff actually affects before a single JVM starts.

All of that can be done from outside — a CLI, a couple of init scripts, an HTTP cache — with no build ownership, and therefore no AGP treadmill. It is also, as it happens, where a commercial product already proves the demand: Develocity sells exactly this, at enterprise prices, closed. BuildBuddy filled that niche for Bazel. For Gradle it was empty.

That's lightning: a self-hosted, Apache-2.0 platform — one Rust binary with SQLite — doing flaky-test radar, build telemetry, remote build cache with analytics, and diff-aware test selection. On nowinandroid, a change in one core module selects 24 of 45 modules; a docs-only pull request is decided in milliseconds, before CI has installed a JDK.

The uncomfortable part of this story is that the interesting question ("could I write a build system in Rust?") had a boring answer, and the boring question ("what's missing around the build?") had the interesting one. I only got there by taking the first question seriously enough to be talked out of it.
